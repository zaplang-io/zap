- **A generic call now enforces type-parameter consistency across its arguments**
  (I#1545, decisions/lang/1545-generic-arg-consistency.md). When a free function
  is generic, binding a type parameter `T` from one argument constrains every
  other argument declared with `T`. With `def option[T](Type[T] kind, T default)`,
  the `Type[T]` argument `int64` establishes `T = int64`, so a mismatched
  `default="oops"` is now `error[ZAP4021]` instead of silently lowering a string
  constant into an `i64` slot. The rule lives in generic checking in general, not
  the decorator desugar: `def take[T](T x, T y)` likewise rejects
  `take(1, "hello")`. Arguments are matched to parameters in declaration order
  (so keyword order is irrelevant), a `Type[T]` binding is authoritative, and an
  ordinary binding widens to the least upper bound — a matching integer default,
  and numeric widening such as `int32`/`int64`, continue to compile. An
  `Unknown`/`py` argument is a wildcard that never forces a binding or a
  conflict. The change is additive (previously every type parameter erased to
  `Unknown`, accepting anything); generic *methods* are a documented follow-up.
  This closes the generic-consistency gap the I#1527 ADR deferred. Unblocks
  zaplang-io/cli#4.
