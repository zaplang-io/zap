- **Fixed-width integer arithmetic is now width-stable in the type system**
  (I#1676, decisions/lang/1654-fixed-width-integer-semantics.md; supersedes the
  promote-to-64 clause of D-0019 / #552). The result of an arithmetic operation
  on fixed-width integers is no longer silently promoted to 64-bit: same-width
  operands keep that width (`uint8 + uint8 → uint8`, `int32 + int32 → int32`),
  mixed-width operands take the larger operand's type (`uint8 + uint16 →
  uint16`, `int32 + int64 → int64`), and an untyped integer literal adopts the
  concrete operand's type (`uint8 + 5 → uint8`) instead of defaulting to
  `int64`; a context-free literal is still `int64`. An untyped integer literal
  inferred into a fixed-width type — a narrow declared/annotated target, the
  adopting operand of an arithmetic op, or an augmented assign — must now be
  representable in that type or it is a compile error (`ZAP4016`); this also
  catches a negative literal assigned into an unsigned type. The explicit
  `uintN(...)` / `intN(...)` conversion is unchanged and remains the wrapping
  escape hatch (D-0019 / D-0020). Signed↔unsigned mixing is still rejected
  (`ZAP4015`). This is the type-system half of the semantic break; the matching
  runtime wrap at the declared width (so `uint8(200) + uint8(100)` evaluates to
  `44`) is tracked in I#1677.
