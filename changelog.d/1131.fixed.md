- **Generic type-argument inference now reads subscript, slice, tuple-literal,
  and comprehension arguments** (I#1131). Completing the family of I#1117
  (unary) and I#1128 (binary): the inferer typed a `list` literal but typed a
  subscript `xs[0]`, a slice `xs[0:2]`, a tuple literal `(1, 2)`, and a
  comprehension `[x for x in xs]` as unknown, so `Optional.Some(xs[0])` failed
  with `ZAP6001` ("cannot infer type argument 'T'") and an untyped
  `auto e = xs[0]` binding carried that unknown into every later use. Each arm
  is now typed, mirroring the language's own rules: a subscript yields the base
  container's element/value type (`list[T]` → `T`, `dict[K, V]` → `V`, `str` →
  `char`, `bytes`/`range` → `int64`); a slice yields the base's own type
  (`list[T]` / `str` / `bytes`); a tuple literal yields `tuple[...]` of its
  element types; and a `list` / `set` / `dict` comprehension yields
  `list` / `set` / `dict` of its element/key-value type, with the loop variable
  now typed from its iterable. An operand the inferer cannot type (a tuple index
  without a static position, a built-in call's result, an opaque base) leaves
  the expression unresolved, so a genuinely unconstrained parameter is still
  rejected. A bare generator expression keeps the unresolved result on purpose
  (its type is a non-nominal iterator the inferer cannot name).
