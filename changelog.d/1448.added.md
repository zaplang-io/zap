- **`http.Client` response-body byte limit** (I#1448,
  decisions/stdlib/1448-http-response-body-limit.md). `http.Client(...)` now
  accepts a `max_response_bytes` keyword that caps each response body **as it is
  received**: `http.Client(max_response_bytes=65536)` rejects any response whose
  body would exceed 65536 bytes, while `max_response_bytes=0` (the default) keeps
  today's unbounded behavior. The cap is enforced across all three framing modes
  — a `Content-Length` larger than the cap is rejected before the body is read,
  and a `chunked` or EOF-framed body is cut off the moment its decoded size
  crosses the cap — so a body of exactly the limit succeeds and the first byte
  over it raises. The error is a new catchable built-in exception
  **`ResponseTooLargeError`** ⊂ `OSError` ⊂ `Exception`, so `except
  ResponseTooLargeError` selects just the over-limit case while `except OSError`
  / `except Exception` still catch it. A partial over-limit response closes its
  connection instead of returning it to the keep-alive pool, so an oversized
  reply can never leave a poisoned socket to be reused. The cap composes with the
  existing `timeout`, `follow`, and `max_redirects` controls; a negative
  `max_response_bytes` is a `ValueError` raised before any dial. This lets a
  client bound its own memory use against an untrusted or oversized endpoint
  (e.g. OAuth provider-metadata discovery) rather than buffering the whole body
  and checking its length afterward.
