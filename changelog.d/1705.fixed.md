- **A generic parameter's default is now type-checked against the type argument
  it is used with** (#1705). When a generic call omitted a defaulted parameter,
  the default was materialized at the call site and passed into the chosen
  specialization without ever being checked against that specialization's
  parameter type. So when the type parameter was pinned by a source other than
  the default — an explicit type argument (`setting[str]()`), the
  expected/return type (`str s = setting()`), or another argument
  (`pair("hi")`) — an incompatible default such as the `bool` `False` of
  `def setting[T](T value=False)` was reinterpreted into the chosen type's slot
  (a `bool` into a `str`/pointer), a type-unsound lowering with no diagnostic.
  Such a call is now rejected with `ZAP4001` ("type mismatch in assignment"),
  using the same assignability rule sema applies to every other assignment. The
  check is per call, so supplying the argument (the default is then unused) is
  unaffected, and conservative: an untyped numeric literal default still fits any
  numeric type argument, and a container/user parameter type or a non-literal
  default is left untouched.
