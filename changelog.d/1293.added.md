- **A `@derive` that cannot apply is now a consumer-grade compile error (E3d)**
  (I#1293, epic #1289 / #1248, decisions/lang/1293-derive-diagnostics-wiring.md).
  A comptime failure inside a derive generator's descent — e.g. a library
  `comptime.error` raised for an unsupported field — now renders as
  `error[ZAP7003]: cannot derive `Trait` for `Type`` pointing at the **user's own
  field** (never the generator symbol or an evaluator internal), with a
  `required because of field `f` of `Type`` note and the library's own message as
  the root cause, located with `file:line:col` and a source snippet. The compile
  fails with a diagnostic, never a panic. A comptime failure outside a derive
  renders as a plain comptime error (`ZAP7002` for a library abort, `ZAP7001` for
  an engine fault) at its own span. This wires the #1256 renderers (shipped
  host-tested over constructed inputs) into the live monomorphization descent,
  consuming the reachable failures #1330 enabled. A valid derive emits no
  diagnostic. First cut: a single backtrace frame (the offending field); the
  multi-level container chain and the dual-span generator-fault form are
  follow-ups, and the rich render is on the front-end path (`zap ir`, analysis,
  `zap check`) — the LLVM `build`/`run` path surfaces the message without a panic.
