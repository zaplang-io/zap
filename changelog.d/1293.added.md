- **A `@derive` that cannot apply is now a consumer-grade compile error (E3d)**
  (I#1293, epic #1289 / #1248, decisions/lang/1293-derive-diagnostics-wiring.md).
  A comptime failure inside a derive generator's descent — e.g. a library
  `comptime.error` raised for an unsupported field — now renders as
  `error[ZAP7003]: cannot derive `Trait` for `Type`` pointing at the **user's own
  field** (never the generator symbol or an evaluator internal), with a
  `required because of field `f` of `Type`` note and the library's own message as
  the root cause, located with `file:line:col` and a source snippet. The compile
  fails with a diagnostic, never a panic. A comptime failure outside a derive
  renders as a plain comptime error (`ZAP7002` for a library abort, `ZAP7001` for
  an engine fault) at its own span. This wires the #1256 renderers (shipped
  host-tested over constructed inputs) into the live monomorphization descent,
  consuming the reachable failures #1330 enabled. A valid derive emits no
  diagnostic. First cut: a single backtrace frame (the offending field); the
  multi-level container chain and the dual-span generator-fault form are
  follow-ups, and the rich render is on the front-end path (`zap ir`, analysis,
  `zap check`) — the LLVM `build`/`run` path surfaces the message without a panic.
- **A bug *inside* a derive generator is a dual-span compile error, never a
  panic (E3d)** (I#1293, decisions/lang/1293-generator-fault-dual-span.md). An
  engine fault in a library generator's own code — e.g. an out-of-range
  `reflect.field` — is the library author's mistake, not the consumer's, so it
  now renders as `error[ZAP7001]: error in comptime generator: …` at the
  generator line with a `note: instantiated here` pointing at the user's derive
  site, rather than the consumer "cannot derive" header. The compiler exits with
  a diagnostic naming both places. A library `comptime.error` abort is unchanged
  (the consumer `ZAP7003` form).
- **A nested `@derive` failure now renders the full `required because of …`
  chain** (I#1293, decisions/lang/1293-multilevel-required-because-chain.md). The
  "multi-level container chain" noted above as a follow-up is now shipped: when a
  generator rejects a type buried in a container
  (`dict[str, list[Widget]]`, a tuple element, an optional's element), the
  `ZAP7003` diagnostic carries one `required because of …` frame per container
  level crossed — the list element, the dict key/value, the optional element, or
  the 1-based tuple element — each naming its container type, ordered inner-first
  and climbing out to the field, before the library's own root-cause note. A bare
  struct field still renders the single field frame, unchanged. Builds on the
  nested-type use-site span (I#1346).
