- **A tuple literal with bare `None` elements now lowers against a declared
  tuple type** (I#1195). Returning `(None, None)` from a function whose declared
  return type is a tuple of options — e.g. `def get() -> (Optional[bytes],
  Optional[bytes])` — used to fail IR lowering with `error[ZAP6001]: this
  expression is not supported by codegen yet (Phase 1 slice)`, even though it
  type-checked and the all-present `(Optional.Some(...), Optional.Some(...))`
  form already worked. The declared tuple type now supplies each element's
  expected type, so a bare `None` element lowers to the canonical empty option
  (the tagged `None` for a scalar payload such as `Optional[int64]`/`Optional[bool]`,
  the null pointer for a pointer payload such as `Optional[bytes]`/`Optional[str]`
  or a reference struct) — extending the #1075/#1080 type-contextual `None`
  mechanism to tuple elements. This covers any typed tuple-literal context
  (returns, call arguments, annotated bindings), including across modules, and a
  bare `None` tuple element against a **non-optional** declared element is still
  rejected with a clear `None is not a valid \`<type>\` value` message.
