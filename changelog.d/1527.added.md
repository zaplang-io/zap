- **A concrete type can now be passed to a library-defined decorator as a
  first-class type value** (I#1527, decisions/lang/1527-type-args-to-decorators.md).
  A bare primitive type name in value position — `int64`, `str`, `bool`,
  `float64`, the sized/unsigned ints, `char`, `bytes`, `bigint`, `complex` — is a
  first-class type value of type `Type[T]`, so the approved Click-style CLI
  surface compiles: `@cli.option("--count", int64, default=1)` /
  `@cli.argument("name", str)`. The type flows through the nested calls the
  stacked imported returning decorators generate (I#1509/I#1519), alongside named
  metadata such as `default=`, and binds a generic library parameter
  (`option[T](str, Type[T] kind, …)` at `T = int64`). Type values are **statically
  distinguishable and invariant** — `Type[int64]` is not `Type[str]`, and (unlike
  the values) there is no numeric widening, so `Type[int32]` is not `Type[int64]`
  — and a **non-type** argument where a `Type[T]` is expected is a precise error
  (`ZAP4021`). At run time a type value is a minimal `int64` type-id token: no
  runtime reflection graph (that is the comptime `reflect.type_info` of I#1257,
  not materialized here), no new IR type, no GC root. Previously a bare type name
  in value position was `error[ZAP3001]: unknown name 'int64'`. Conversion call
  forms (`int64(x)`, `str(x)`) are unchanged. User struct/enum type values (the
  type-vs-constructor ambiguity) and a run-time id reader are deferred follow-ups.
  Unblocks zaplang-io/cli#4.
