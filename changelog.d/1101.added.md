- **Borrowed-bytes `strview` — a non-owning string view for read-only consumers**
  (I#1082, PR#1101, decisions/lang/1082-borrowed-bytes-strview.md; RFC discussion
  #1097). A `strview` names an existing string's bytes with **zero heap allocation
  and zero copy** for the read-only consumers that never retain the bytes. **Create**
  it explicitly: `s.view()` (whole string), `s.view(lo, hi)` / `s.view(lo)`
  (codepoint-indexed, D-0025), and sub-view with `v.view(lo, hi)`; `str[a:b]` slice
  semantics are unchanged, so views are opt-in. **Consumers:** `v in d` and
  `d.get(v[, default])` on a `str`-keyed dict probe the borrowed bytes directly (no
  transient key); `v == "..."` / `v == w`; `len(v)` / `v.len()`; `v.__hash__()`
  (identical to the materialized string's seeded wyhash); `v.startswith(...)` /
  `endswith` / `contains` (argument may be a `str` or a `strview`); and `v.to_str()`
  to materialize an owned copy. **Soundness:** a `strview` is affine — it may not be
  a struct field, module global, collection element / dict key-or-value, or function
  return type (`ZAP5135`); a bare local or a parameter is always sound because the
  view carries its backing as a traced pointer (rewritten on a moving-GC evacuation
  via the #586 aggregate-root pairs — the base+offset representation). Owning /
  mutating string methods are absent by design: materialize with `.to_str()` first.
  Experimental (docs/STABILITY.md); adding the type reserves the `strview` keyword.
