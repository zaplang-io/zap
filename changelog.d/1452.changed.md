- **An `Optional[T]` payload-type mismatch is now caught at the type-checking
  layer, not only at `zap build`** (I#1452). Sema previously erased the `Optional`
  payload (tracking every `Optional[T]` as opaque `Named("Optional")`), so a
  payload mismatch — `Optional[int64] y = Optional.Some(9223372036854775808)`
  (#1379), or `Optional.Some(g)` for a `bigint g` / `int32 n` / `str` into an
  `Optional[int64]` (#1407) — type-cleaned through the sema-only surface and was
  only rejected later in IR lowering. Sema now tracks `Optional[T]` with its
  payload preserved (`Ty::Optional(T)`, like `list[T]`/`dict[K, V]`) and is
  payload-aware: `Optional[U]` is assignable to `Optional[T]` iff `U == T`, so the
  mismatch is a sema `error[ZAP4001]` surfaced through `check` / the MCP
  `check_source` tool / the LSP, as well as at `zap build`. This is a
  diagnostic-surface change only — **no program's end-to-end accept/reject
  behaviour changes** (the lowering checks remain as defense in depth) and **no
  new implicit conversion is added** (in particular no `Optional[int32] →
  Optional[int64]` widening). The #1265 bare-payload wrap (`Optional[int64] x = n`
  for a bare numeric `n`) is unchanged, except the locked #1379 reject of a bare
  `bigint` into a fixed-width-numeric payload now also surfaces in sema. A matching
  payload, bare `None`, `Optional.None`, and nested `Optional[Optional[T]]` are
  accepted as before; diagnostics now render the precise `Optional[int64]` rather
  than a bare `Optional`.
