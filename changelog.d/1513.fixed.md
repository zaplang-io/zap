- **`list(iterable)` / `set(iterable)` / `tuple(iterable)` now preserve
  `bool` / `char` element identity** (I#1513,
  decisions/lang/1513-ctor-comprehension-bool-char-narrows.md). Building a
  container from a `list[bool]` / `list[char]` source rendered (and read back)
  the elements as their physical `int64` storage word — `tuple([True, False])`
  printed `(1, 0)`, `list([True, False])` printed `[1, 0]`, and a char source
  printed decimal codepoints — because the general D-0048 iteration protocol
  yielded the storage word and the constructors re-derived an `int` element from
  it. The protocol now narrows a `bool`/`char` element back to its logical type
  at a single chokepoint (`iterate_list_logical`), so the constructors print
  `(True, False)` / `[True, False]` / `['a', 'b']` with CPython parity. The same
  narrowing flows through comprehensions (`[b for b in bools]`), `*xs` splats,
  and the `oset[T]`/`set[T]` typed constructors (which no longer reject a
  `bool`/`char` source with a spurious "same representation" error). A direct
  `[True, False]` literal was always correct and is unchanged; the physical
  storage, GC tracing, and the wrong-element-kind guard are untouched. Extends
  the statement-`for`/indexing read-back narrowing of I#1241 to the remaining
  user-facing read path it had left as a follow-up.
