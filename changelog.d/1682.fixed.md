- **A generic call now enforces type-parameter consistency through an
  `Optional[T]` parameter** (I#1682, decisions/lang/1682-optional-payload-consistency.md).
  This completes the #1545 rule for the Click-style CLI option signature
  `def select[T](Type[T] kind, Optional[T] fallback = None)`. The `Type[int64]`
  argument establishes `T = int64`, so a raw `fallback="oops"` — which lifts into
  the payload by implicit `Some` wrapping (#1265) — must be compatible with
  `int64`; it is now `error[ZAP4021]` instead of silently lowering a string
  constant into an `Optional[int64]` slot. A matching integer payload (by name or
  position, with numeric widening such as `int32` into `Optional[int64]`) still
  lifts; omission and an explicit `None` still work; an explicitly wrapped
  matching `Optional[int64]` still compiles, and a wrongly wrapped `Optional[str]`
  is likewise rejected. The root cause was that `resolve_type_scoped` had no
  `Optional` arm, so an `Optional[T]` parameter erased its payload to `Unknown`
  and the consistency pass could not see the payload's type variable; the fix
  preserves the payload type variable and treats the bare-payload lift as a
  binding of `T`. Preserving the payload type variable also completed the #1623
  generic-return substitution for `Optional` (and `tuple[T]`), so
  `wrap[T](T x) -> Optional[T]` now types a `str` call as `Optional[str]` rather
  than the unsubstituted `Optional[T]`. Unblocks safe typed defaults in
  zaplang-io/cli#4.
