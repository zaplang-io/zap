- **`fractions` — exact rational `Fraction` type** (I#982,
  decisions/stdlib/982-fractions-exact-rational.md, epic #966). A software
  arbitrary-precision rational built over the prelude `bigint`
  (numerator + positive denominator, always reduced to lowest terms with a
  normalized sign) — pure prelude Zap, no runtime C, the exact-number companion
  to `decimal`. The headline guarantee is exactness: `Fraction(1, 3) +
  Fraction(1, 3) + Fraction(1, 3) == Fraction(1)`, which binary `float64` cannot
  give. **Surface:** `import fractions` then `fractions.Fraction(3, 4)` /
  `Fraction(7)` / `Fraction("3/4")` / `Fraction("0.25")` (type written bare as
  `Fraction`). **Arithmetic:** `+ - * /` are all exact (the result is auto-reduced
  — rational division needs no precision argument); dividing by a zero fraction
  raises `ValueError`. **Also:** `numerator()` / `denominator()` accessors,
  `limit_denominator(max_denominator=1000000)` (closest fraction within a
  denominator bound, via continued-fraction convergents), `to_float()`,
  comparisons (value equality — `Fraction(2, 4) == Fraction(1, 2)`), and `str()`
  rendering `num/den`. **No lossy float construction:** `fractions.Fraction(
  <float>)` is a compile error — construct an exact decimal from its `str`.
  Divergences from Python (see `docs/PYTHON_DIFFERENCES.md`): no implicit
  `int → Fraction` promotion for operators (mix via `Fraction(k)`); a float
  argument is rejected; a signed denominator in a ratio literal (`"1/-2"`) is
  rejected; `numerator`/`denominator` are methods returning `bigint`;
  `ZeroDivisionError` maps to `ValueError`.
