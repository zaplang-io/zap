- **Tuple types can now be used as explicit generic type arguments** (I#1478,
  I#1479). The monomorphizer could not take a tuple type as a type argument,
  breaking generic calls that carry one — `run[(Optional[bytes],
  Optional[bytes])](...)` failed IR lowering with `error[ZAP6001]: this
  expression is not supported by codegen yet (Phase 1 slice)` when an argument
  element was a bare `None` (#1478), and `run[dict[bytes, (bytes, bytes)]](...)`
  was mis-lowered as a field access, `error[ZAP6001]: no field 'run' on struct`,
  because the nested tuple made the whole type argument unresolvable (#1479).
  `expr_to_type` now understands tuple types, and a tuple written in a generic
  subscript is split into separate arguments only when its arity matches the
  generic's declared parameter count — `dict[K, V]` / `f[A, B]` still split,
  while a one-parameter `run[(A, B)]` binds `T` to the whole tuple and a nested
  one-parameter generic over a tuple (`Optional[(A, B)]`, `list[(A, B)]`)
  resolves correctly. The parser renders `g[A, B]` and `g[(A, B)]` identically,
  so arity is the only disambiguator. Unblocks zaplang-io/memcached#9.
