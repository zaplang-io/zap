- **Reassigning a returned `value struct` to an already-existing aggregate field
  (`obj.field = f()`) now boxes it onto the heap, fixing a dangling-pointer
  corruption** (I#1446, decisions/lang/1400-value-struct-field-boxing.md). This
  was the one field-store site the #1400 fix did not reach. #1400 boxed value
  structs stored during construction (`Struct(field=f())`), into tagged
  enum-variant payloads, and the `#1262` `Optional.Some` auto-wrap, but the
  field-*assignment* statement arm still used the lvalue-only `copy_if_value`. A
  flat `value struct` returned by value is physically a register / `sret` **stack
  spill** (D-0051), and a field holds a *pointer* to its value struct's storage;
  reassigning a returned (non-lvalue) value struct straight into an existing
  field stored that spill's pointer, so the field **dangled** once the producing
  frame returned and a later read came back corrupted. A `_ProbeCursor` that
  cached `self.seed = self._make_seed()` (a returned `DateTime`) and read it back
  on the next call saw `0000-00-00T02:00:00` instead of `2024-01-31T02:00:00`;
  the datetime-utils recurrence iterator hit the same shape caching a returned
  `DateTime` seed. The field-assignment arm now routes through the same
  `copy_field_value` chokepoint as the construction / enum-payload / Optional
  stores, boxing an inline-eligible value struct (a fresh heap `StructNew` +
  field copy) so the field owns heap storage that outlives every frame. Value
  semantics are unchanged (an lvalue-read reassignment still copies), and
  reference structs and non-struct fields are unaffected.
