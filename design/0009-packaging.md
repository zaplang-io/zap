# Proposal: Package manager & project environment (`zap add`/`zap zenv`)

- **Author(s):** Zap toolchain team
- **Last updated:** 2026-10-19
- **Status:** Accepted
- **Discussion:** issue #69 (follow-up of #56); DECISIONS.md D-0052, D-0035, D-0053

> Formatting convention (from Go): wrap near the 80-column mark and start each
> sentence on a new line.

## Abstract

This proposal specifies the concrete file formats, resolution algorithm, and
tooling for Zap's package manager and project environment, implementing the
design locked in D-0052.
A project is described by an author-edited `zap.toml` and a tool-generated,
committed `zap.lock`.
Dependencies are selected with Go-style Minimal Version Selection (MVS) over
semver versions, resolve to decentralized VCS (or local `path`) sources, and are
integrity-checked with a content hash.
`zap zenv` creates a project-local, env-var-activated environment that points
both Zap module resolution and the embedded CPython (#27) at project-local
caches.

## Background

Today the toolchain (D-0053, PR #87) scaffolds a `zap.toml` with `zap new`/`zap
init` but has no dependency management: `zap add`, `zap remove`, and `zap zenv`
are stubs that exit 2, and project-mode `zap run`/`zap build` resolve only
`zap.toml` → `src/main.zap` with no dependencies.
D-0035 locked the direction (one bundled tool, manifest + lockfile + semver,
Cargo/Go-modules style, explicitly **not** pip/PyPI) and D-0052 locked the
concrete design (MVS, decentralized VCS sources, a checksum database, and the
`zenv` dual environment).
This proposal turns D-0052 into file formats, an algorithm, and a CLI.

## Proposal

### Manifest — `zap.toml`

Author-edited, TOML, Cargo-style.
The shape emitted by `zap new`/`zap init` is preserved and extended:

```toml
[package]
name = "myapp"
version = "0.1.0"

[dependencies]
# logical name -> source + semver (D-0052, D-0028):
jsonlib = { git = "https://example.com/jsonlib.git", version = "1.4.0" }
mathx   = { path = "../mathx" }          # local source (Go-style replace)
```

A dependency value is a table with exactly one **source** key plus an optional
version requirement:

- `git = "<url>"` — a VCS source. Requires `version = "<semver>"` (the minimum
  version, resolved against the repo's semver tags, e.g. tag `v1.4.0`).
- `path = "<dir>"` — a local directory containing a `zap.toml`. Fully resolvable
  offline; its own version is read from its `[package]` table.

The source uses the **logical name** (the table key); `import jsonlib` and
`import jsonlib as j` (D-0028) bind to it.

### Lockfile — `zap.lock`

Tool-generated and **committed**, TOML.
It records the fully-resolved build list (every direct and transitive module,
the exact version MVS selected) and an integrity hash, so a checkout rebuilds
identically:

```toml
# generated by `zap`; do not edit by hand.
version = 1

[[module]]
name = "jsonlib"
version = "1.4.0"
source = "git+https://example.com/jsonlib.git"
checksum = "zap1:9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"

[[module]]
name = "mathx"
version = "0.2.0"
source = "path+../mathx"
checksum = "zap1:…"
```

`checksum` is `zap1:` followed by the lowercase hex SHA-256 of the module's
**canonical content hash** — a hash over the sorted `relpath\0sha256(bytes)\n`
lines of every file in the module tree (the Go `h1:` idea, simplified to a flat
hex digest).
The set of `(name, version) → checksum` rows is the project's slice of the
decentralized **checksum database** (D-0052); a shared `zap.sum`/proxy is a
future extension (see Open issues).

### Resolver — Minimal Version Selection

Versions are semver.
A **major version is the compatibility boundary**: the module identity used by
the resolver is `(name, major)`, so `foo` v1 and `foo` v2 are distinct modules
that may coexist (Go's "different major = different module path").

MVS selects, for each module identity, the **maximum of the minimum versions**
required anywhere in the graph:

1. Start from the root manifest's direct requirements.
2. For each required `(module, min_version)`, load that module@version's own
   requirements and recurse, visiting each `(module, version)` once.
3. The selected version of a module is the greatest `min_version` demanded of
   that `(name, major)` across the whole graph.

This is deterministic and reproducible by construction — no SAT solver, no
"latest compatible" drift, no dependency hell.
Two different majors of the same name are allowed; two incompatible majors are
never *unified* (they simply coexist), so the only hard error is a malformed or
missing requirement.

### CLI

All new behavior lives behind these verbs (D-0053); argument parsing stays
hand-rolled (the workspace keeps its tiny dependency surface).

- `zap add <name> --git <url> --version <semver>` — add a VCS dependency.
- `zap add <name> --path <dir>` — add a local dependency.
  Both insert/update `[dependencies].<name>` in `zap.toml`, re-run MVS, and
  rewrite `zap.lock`.
- `zap remove <name>` — drop the dependency from `zap.toml` and re-lock.
- `zap zenv create [--no-venv]` — create the project environment (below).
- `zap zenv status` — print whether a zenv exists / is active and its paths.
- `zap zenv path` — print the active Zap module search path (honors
  `ZAP_ZENV`); used to demonstrate that activation flips resolution.
- `zap zenv clean` — remove the `zenv/` directory.

`zap add`/`remove` require a `zap.toml` (run `zap init` first) and leave a
re-locked `zap.lock`.

### `zenv` — the project environment

`zap zenv create` builds:

```
zenv/
  activate        # `source zenv/activate` (bash/zsh)
  pkg/            # project-local Zap module cache (materialized from zap.lock)
  venv/           # standard Python venv (python3 -m venv), unless --no-venv
```

`source zenv/activate` is venv-simple: it sets environment variables and
defines a `deactivate` shell function that restores them.
Activation sets:

- `ZAP_ZENV=<abs>/zenv` — marks the environment active and points Zap module
  resolution at `$ZAP_ZENV/pkg` instead of the global cache.
- `VIRTUAL_ENV=<abs>/zenv/venv` and `ZAP_PYENV=<abs>/zenv/venv` — the nested
  Python venv for the embedded CPython (#27).
- `PYTHONPATH=<abs>/zenv/venv/lib/python*/site-packages:$PYTHONPATH` — so the
  embedded interpreter (`Py_InitializeEx`, zaprt.c) picks up the venv's packages
  **with no runtime change** (see Compatibility).
- `PATH=<abs>/zenv/venv/bin:$PATH` — so `python`/`pip`/`uv` in the shell use the
  venv.

`deactivate` unsets `ZAP_ZENV`/`ZAP_PYENV` and restores the pre-activation
`VIRTUAL_ENV`/`PYTHONPATH`/`PATH`.

Zap module resolution consults `module_search_paths()`: when `ZAP_ZENV` is set it
returns `$ZAP_ZENV/pkg`; otherwise the global cache (`$ZAP_CACHE` or an OS
default).
Materialization copies/clones each locked module into `$ZAP_ZENV/pkg/<name>`;
`path` sources are copied (hermetic, offline), `git` sources are cloned at the
selected tag when the network is available.

## Rationale

- **MVS over a SAT solver (D-0052, D-0035):** MVS is a dozen lines, deterministic,
  and needs no lockfile to be *correct* (the lock is a cache/integrity record,
  not the source of truth) — the Go insight. It is the deliberate opposite of
  pip's backtracking resolver and npm's "latest that fits."
- **`(name, major)` identity:** faithfully implements "major = compatibility
  boundary" and lets v1 and v2 coexist, which MVS needs to avoid false conflicts.
- **`path` sources in addition to `git`:** Go has them (`replace`/local modules);
  they make local multi-module development and **hermetic tests** possible
  without a network or a git server, while `git` remains the distribution story.
- **Content hash, hand-rolled SHA-256:** integrity is core to the decentralized
  model (D-0052), but one well-known hash does not justify pulling the
  `sha2`/`digest`/`generic-array` crate chain into a workspace whose only
  external dependency is `inkwell`. A self-contained, test-vector-checked
  SHA-256 keeps the dependency surface tiny.
- **`toml` + `serde` + `semver` crates:** per the issue's guidance to prefer a
  small, well-maintained crate; `semver` is already in the local cargo cache and
  is the canonical implementation, and `toml`/`serde` are the idiomatic,
  round-trip-safe choice for the manifest and lock. They are pinned to exact
  versions (the workspace does not commit `Cargo.lock`).
- **`PYTHONPATH` bridge for the venv:** D-0052 says activation sets `VIRTUAL_ENV`
  + `ZAP_PYENV` "so the embedded CPython uses it," but the embedded interpreter
  is started with `Py_InitializeEx` (zaprt.c), which does not honor `VIRTUAL_ENV`
  on its own and is owned by the runtime/scheduler work (#80) — out of scope to
  edit here. Setting `PYTHONPATH` to the venv's `site-packages` makes the venv
  **actually functional today** through the stock `site` machinery, with no
  runtime change; teaching the interpreter to honor `ZAP_PYENV`/`VIRTUAL_ENV`
  directly (via `PyConfig`) is a small, clearly-scoped runtime follow-up.

## Compatibility

- **Additive.** `zap new`/`zap init` still emit the same `zap.toml`; the only
  manifest change is that `[dependencies]` entries are now meaningful.
- The `add`/`remove`/`zenv` stubs are replaced; the CLI `stubs_name_their_owning
  _tickets` test is updated to cover only the still-stubbed `mcp` (#72).
- No IR-schema or runtime-ABI boundary is touched.
- The embedded CPython is **not** modified; the venv works via `PYTHONPATH`.
- Zap-to-Zap `import` of packages is not yet implemented in the compiler
  front-end (only `import python` exists today); this proposal lands the manifest,
  lock, resolver, checksum, cache materialization, and `module_search_paths()`
  that the front-end will consume when Zap-package imports land.

## Implementation

1. New crate `crates/pkg` (`zapc_pkg`), in the host default-members so `cargo
   test` builds it: `manifest`, `lockfile`, `semver`-backed `resolver` (MVS),
   `checksum` (SHA-256 + tree hash), `zenv` (layout, activate-script, search
   paths, materialize), and a thin `ops` layer (`add`/`remove`/`zenv_*`).
2. `crates/driver` depends on `zapc_pkg`; the `Add`/`Remove`/`Zenv` CLI arms call
   `ops`. `Zenv` gains a subcommand (`create|status|path|clean`). Edits in
   `cli.rs` stay confined to those arms (the `mcp` arm is owned by #72).
3. Tests: MVS unit tests (incl. major-boundary coexistence and max-of-mins),
   manifest+lock round-trip, SHA-256 vectors, and `zap`-binary integration tests
   for `zap new` + `zap add --path`, lock generation, and `zenv`
   create/activate/path flip.

Nothing here touches a phase boundary; it can proceed in parallel with #72
(disjoint CLI arm) and #80 (runtime, untouched).

## Open issues

- A shared `zap.sum`/official caching proxy (the cross-project checksum database
  and mirror) is deferred; this lands the per-project integrity rows only.
- `git` fetch/clone during `zap add` is best-effort and recorded with the
  selected version; computing the real checksum of a `git` source requires a
  fetch and is filled at materialize time. Offline `path` sources get full
  checksums immediately.
- Teaching the embedded interpreter to honor `ZAP_PYENV`/`VIRTUAL_ENV` directly
  (`PyConfig`) is a runtime follow-up (#80 territory); `PYTHONPATH` bridges it
  for now.
- Multi-import (`import (a, b, c)`) implementation is staged (grammar reserved,
  D-0052).
