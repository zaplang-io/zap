- **Discussion:** I#100 (parent I#79; scope set by DECISIONS.md D-0056).

> Formatting convention (from Go): wrap text near the 80-column mark and start
> each sentence on a new line.

## Abstract

A native (no-CPython) `json` module for Zap, offered in three coexisting access
modes layered on one streaming scanner core: a dynamic `json.Value` DOM with
Python-familiar `loads`/`dumps`, a compile-time typed codec driven by a new
built-in `@derive(Json)`, and a public pull/token scanner that ties into the
Iterator protocol (D-0048) for large or over-the-wire payloads.
All design forks are **locked** as of 2026-10-20 (the "Decisions" section
records each); the inline *(rec)* notes throughout are the accepted choices.
Work is sequenced **substrate-first**: a shared, Zap-level, derive-driven
codec/reader substrate (phase 1, I#131), then `json` on top (phase 2, I#100),
then `csv` on top (phase 3, I#132).

## Background

The reuse check in I#100 concluded `msgspec`/`orjson` are CPython C-extensions
and therefore not reusable for a bundled-std module (D-0056); `json` must be a
**native** implementation.
`msgspec` remains a *design reference* for the typed/schema-driven surface, not a
dependency.

`json` is high-leverage: it gates the official AWS package (I#89) and the
FastAPI-style web framework (I#107), both of which want **typed** request/response
structs.

What the language already provides (all landed) and what the design must respect:

- **Data-carrying enums** (D-0046, PR #62): `enum` with type-first named payload
  fields, value-first tagged representation, `match` exhaustiveness.
  *Non-generic* enums ship today — so a fixed-variant `json.Value` enum is
  expressible now.
- **Iterator protocol** (D-0048, PR #68) + **generators** (I#67, PR #118):
  comma-ok `__next__(self) -> (T, bool)`; a pull scanner can be an `Iterator`.
- **Decorators / `@derive`** (D-0036): built-in derives (`Eq`/`Ord`/`Hash`/`Repr`)
  are *compiler-known* codegen over struct fields, wired into sema + lower.
  Field/struct annotations (`@json(name=...)`, `@default`) are supported.
  Crucially, a built-in `@derive(Json)` needs **no user-macro machinery** — it is
  another compiler-known derive. `design/0006` line 398 lists `@derive(Json)` as
  "deferred"; this proposal un-defers it as the core of the typed path.
- **Module seam** (I#121, PR #122): per-crate `modules/<name>.rs` with a
  `ModuleCheck { name, check }` dispatch on `module.method(args) -> Option<Ty>`.
  `str`/`bytes` share the `ZapStr` runtime layout and both lower to `Ty::Ptr`.
  Built-ins `list`/`dict`/`set` exist.
- **Exceptions** (I#12/PR #40): `raise` currently carries a **string** message;
  typed exception classes are not yet first-class.

What is **staged, not landed**, and therefore cannot be depended on for v1:

- **User generics** (D-0017): so a generic `json.decode[T](s)` function and the
  generic `Optional[T]`/`Result[T, E]` enums (`design/0006` line 585) are **not
  expressible yet**.
  This is the single biggest constraint on the typed surface and shapes the whole
  recommendation.

## Proposal

### 1. Architecture: one scanner core, three modes

```
                 ┌─────────────────────────────┐
   bytes / str → │  scanner core (tokenizer)   │  internal, SIMD-ready layering
                 └──────────────┬──────────────┘
          ┌──────────────┬──────┴───────┬────────────────┐
          ▼              ▼              ▼                 ▼
   json.loads →    @derive(Json)   json.Scanner     (fast-follow)
   json.Value DOM  from_json/      pull/token API   socket Decoder
                   to_json methods  (Iterator)       over netpoller/http
```

A single hand-written scanner produces JSON tokens.
`loads` folds tokens into a `Value` tree; the typed codec maps a `Value` into a
struct (v1) with a token-direct fast path as a later optimization; the public
`Scanner` exposes the tokens directly as an `Iterator`.
One scanner, one set of lexing/number/escape rules, one error surface.

**Parser strategy (fork P):** v1 uses a **simple recursive-descent / hand-written
scanner**, not a SIMD-first design.
Rationale: correctness, debuggability, no new dependency, and the design session
host (and CI) is memory-constrained.
The token API is defined so a simdjson-style SIMD "stage 1" structural scan can
replace the byte loop later **without changing** the token surface or any caller.
*Recommendation: recursive-descent for v1; SIMD a measured fast-follow.*

### 2. Dynamic DOM — `json.Value`

A fixed-variant data-carrying enum (expressible today, D-0046):

```python
enum Value:
    Null
    Bool(bool b)
    Int(i64 i)
    Float(f64 f)
    Str(str s)
    Array(list[Value] items)
    Object(dict[str, Value] fields)
```

**Number model (fork N):** split `Int(i64)` / `Float(f64)` rather than JS-style
"all numbers are f64".
A number literal with no fraction and no exponent that fits `i64` decodes to
`Int`; otherwise `Float`.
This matches Zap's typed ethos and lets typed decode into an `i64` field be exact.
*Limits (documented):* integers outside `i64` range decode to `Float` (lossy
beyond 2^53); arbitrary-precision `BigInt` and a lossless `RawNumber(str)` variant
for byte-exact round-trip are **deferred**.
*Recommendation: `Int`/`Float` split with documented limits.*

Object representation is `dict[str, Value]`; **key order is not preserved** in v1
(JSON objects are unordered).
An ordered-object option (riding the `collections` ordered dict, D-0056) is a
minor fast-follow if round-trip order matters for I#107.

Public DOM API (Python-familiar):

```python
json.loads(s: str | bytes) -> Value          # parse; raises on malformed input
json.dumps(v: Value, indent: i64 = 0) -> str  # indent=0 compact, >0 pretty
```

`Value` carries small ergonomic helpers (methods on the enum, D-0046 allows
them), e.g. `v.get(key) -> Value` (object index, `Null` if absent),
`v.at(i) -> Value`, `v.as_int()/as_str()/...` accessors that raise on a variant
mismatch.
Schemaless consumers `match` on `Value` directly with exhaustiveness checking.

### 3. Typed codec — `@derive(Json)` (the high-value path)

Because generics are staged, the typed surface is delivered as a **built-in
derive that generates methods on the type**, needing neither generics nor user
macros:

```python
@derive(Json)
struct User:
    i64 id
    str name
    @json(name="email_address") str email
    bool active = true          # @default via = ; missing key → this value
```

`@derive(Json)` generates, per type `T`:

- `T.from_json(s: str | bytes) -> T` — a type-associated constructor.
- `self.to_json() -> str` and `self.to_json_pretty() -> str`.
- internal dunders `__from_json_value__(v: Value) -> T` and
  `__to_json_value__(self) -> Value` (the DOM bridge; also the extension point for
  the future generic `json.decode[T]`).

v1 implements decode as **`Value` → struct mapping** (parse to DOM, then populate
fields) and encode as **struct → `Value` → string**.
This is simple and correct; a **token-direct** decode that skips the intermediate
`Value` (msgspec-style, zero intermediate allocation) is a perf **fast-follow**
(fork T).
*Recommendation: DOM-map for v1.*

**Field ↔ key mapping:**

- Default key = the exact field name.
- `@json(name="...")` renames one field.
- Struct-level `@json(rename_all="camelCase"|"snake_case")` is a **fast-follow**
  (nice-to-have, not v1).

**Optional / missing / null** *(updated I#165, D-0065 — generics have landed):*

- An **`Optional[T]` field** is *the* way to say "nullable / may be absent"
  (D-0065). On decode, an **absent key or an explicit JSON `null`** yields
  `Optional.None`; a present non-null value yields `Optional.Some(decode(v))`. On
  encode, `Optional.None` **omits the key entirely** (chosen over emitting
  `null`), and `Optional.Some(v)` emits the inner value — so absent↔`None` and
  present↔`Some(v)` round-trip cleanly. The inner `T` may be any type the derive
  already supports (scalars, `str`, nested `@derive(Json)` struct).
- A field with a `@default` (the `=` form, D-0038) uses its fallback value when
  the key is absent — an *honest default*, matching Python dataclass / pydantic
  defaults. (`@default` no longer doubles as the optionality marker; that was a
  pre-generics workaround, now replaced by `Optional[T]`.)
- A non-optional field with no `@default` is lenient for v1 (a missing or
  type-mismatched key yields the accessor's zero value); strict
  missing-key/`null` errors are a follow-up (fork E).
- **Unknown keys are ignored by default** (forward-compatible, web-friendly);
  struct-level `@json(deny_unknown=true)` opts into strict rejection.

**Type coverage:**

| Zap type | JSON |
|---|---|
| `struct` / `value struct` | object (value struct decoded by value) |
| `i64`/`f64`/`bool`/`str` | number / number / bool / string |
| `list[T]` / `set[T]` | array |
| `dict[str, V]` | object |
| tuple `(A, B)` | array, by position (fixed arity) |
| data-carrying `enum` | **internally tagged** object (below) |
| payload-free `enum` | string (the variant name) |

**Enums / sum-types:** default **internally-tagged** representation — a
discriminant key plus the variant's payload fields:

```json
{ "type": "Circle", "r": 3.0 }
```

The tag key defaults to `"type"`, overridable with
`@json(tag="kind")` on the enum; decode `match`es the tag then populates the
variant's fields (reusing D-0046 construction).
**Adjacent** and **untagged** representations are deferred.

### 3b. AWS codec hooks (I#346, D-0086)

AWS JSON shapes need three things plain derive lacks. Each is **opt-in** per
field or type; non-AWS derive behavior is unchanged. The aws-codegen layer
(I#347) emits shape types that use them.

**Timestamps.** A `DateTime` field (the prelude value struct) serializes in a
wire form chosen per field with a field decorator:

```python
@derive(Json)
struct Event:
    DateTime at                   # default: epoch seconds (JSON number)
    @json(timestamp="iso8601")
    DateTime seen                 # ISO-8601 (JSON string)
```

- `@json(timestamp="epoch")` — JSON **number**, Unix seconds (UTC). **This is the
  default** when a `DateTime` field carries no decorator, matching the AWS awsJson
  protocols' default `timestampFormat`.
- `@json(timestamp="iso8601")` — JSON **string**, `2023-11-14T22:13:20` (UTC).

Encode reads the six civil fields and calls the `datetime` runtime
(`zap_datetime_to_unix` / `zap_datetime_format_iso`); decode rebuilds a UTC
`DateTime` from the epoch seconds (`__json_as_int` / `zap_datetime_parse_iso`).

**Blob members.** A `bytes` field is **type-driven** — no annotation: it
serializes to a base64 (standard alphabet, padded) JSON string and parses back
exactly, via `encoding/base64`. Because `bytes` and `str` are distinct types
(`Ty::Bytes` vs `Ty::Ptr`) even though they share the `ZapStr` layout, the derive
routes a blob to base64 and a plain string to escape-and-quote with no ambiguity.

```python
@derive(Json)
struct Blob:
    bytes data        # b"foobar" <-> "Zm9vYmFy"
```

**Open enums.** An enum marked `@json(open)` is a forward-compatible string enum:
each known (payload-free) variant maps to its name, and a string the enum does
not recognize decodes to an `Unknown(value)` fallback variant carrying the raw
string (so AWS adding a value never breaks a client); `Unknown` serializes back
to its carried string.

```python
@derive(Json)
@json(open)
enum Flavor:
    Vanilla                 # <-> "Vanilla"
    Chocolate               # <-> "Chocolate"
    Unknown(str value)      # any other string <-> its raw text
```

The enum must be a tier-3 enum (D-0046) with payload-free known variants and
exactly one `Unknown(str)` fallback variant; at least two known variants are
required (a single known variant beside `Unknown(str)` collapses into the
`Optional` niche, D-0064, which has no tag to switch on). `@derive(Json)`
generates `to_json`/`from_json`/`from_json_value` on the enum — the first enum
JSON derive — so an open enum also nests as a struct field. A **closed** string
enum (no `@json(open)`, strict on unknown) is a follow-up; `@derive(Json)` on an
enum without `@json(open)` is a compile error.

**Validation / error semantics (fork E):** typed decode is **strict**
(msgspec-like) — type mismatch, missing required key, bad enum tag, and (unless
`@default`) `null` are all errors.
The one lenient default is *ignore unknown keys*.
Errors **surface as exceptions**: v1 `raise`s a JSON error whose **string message**
embeds the byte offset and the JSON path (e.g. `$.users[2].id: expected int, got
string`), since typed exception classes are not yet first-class (I#12).
When typed exceptions land, this becomes a `json.DecodeError` carrying structured
`offset`/`path` fields — API-compatible.
*Recommendation: strict typed validation; exceptions with path+offset in the
message for v1.*

### 4. Streaming / pull — `json.Scanner`

The scanner core is internal regardless; the **fork S** is whether to expose a
public pull API in v1.
It is cheap once the core exists, so the recommendation is to ship a **minimal**
one in v1:

```python
enum Token:
    BeginObject; EndObject
    BeginArray;  EndArray
    Key(str k)
    Null
    Bool(bool b)
    Int(i64 i)
    Float(f64 f)
    Str(str s)

json.scan(src: str | bytes) -> Scanner   # Scanner is an Iterator[Token]
```

`Scanner` implements the Iterator protocol (D-0048) with comma-ok
`__next__(self) -> (Token, bool)`, so `for tok in json.scan(body):` just works and
consumes constant memory over a huge array/object.

**Incremental over the wire (fast-follow, ties to I#104/I#107):** a
`json.Decoder` that pulls bytes from an io reader / socket as they arrive from the
netpoller, so an HTTP body is parsed as it streams.
The pull core above is exactly what it is built on; it is deferred only to keep v1
bounded and because it co-designs with `http` (I#104).

### 4b. Reuse across formats — a shared serde substrate (not a shared scanner)

A natural question: should the scanner core be a reusable module other
serde-style modules (`csv`, a future `xml`/`msgpack`/`toml`, the official
non-core packages of D-0056/D-0052) build on?

**The recursive-descent *scanner* is not the reusable asset.**
A JSON tokenizer encodes JSON's grammar, escape rules, and number syntax; CSV,
XML, and msgpack share none of that byte-level logic, so a "universal scanner"
would just be the JSON scanner in disguise.
The hot per-byte scan stays **format-specific** (and may live in `zaprt.c` per
format).

**What *is* reusable lives one layer up** — the same two seams that give serde
its leverage (serde's power is not a shared parser; it is the shared
`Serialize`/`Deserialize` contract plus a visitor/sink, with a thin per-format
impl):

1. **The codec protocol `@derive` targets.** The field-walking, key↔field
   mapping, optional/`@default` handling, enum tagging, and error-path tracking
   that `@derive(Json)` generates are format-neutral.
   If the generated dunders are defined against a **format-neutral visitor/sink**
   interface, `@derive(Csv)`, `@derive(Msgpack)`, etc. all reuse that machinery
   instead of each reimplementing it.
2. **The incremental byte-reader** the scanner pulls from (an `io.Reader`-like
   pull source over `str`/`bytes`/socket).
   Format-agnostic, and the netpoller/`http` body streaming (I#104/I#107) wants
   it anyway — worth making shared from day one.

Two constraints on *where* and *how*:

- **Put the reusable part at the Zap level, not in `zaprt.c`.** A substrate that
  is derive-generated Zap code + a Zap-level reader/visitor protocol is reusable
  by any non-core package; a C-runtime-ABI substrate is not extensible from
  outside. Keep the hot scan in C per format; keep the serde substrate in Zap.
- **For our own built-in derives it needs no staged features.** `@derive(Json)`
  and `@derive(Csv)` are both *compiler built-ins* emitting against the shared
  visitor/sink — no user generics, no user macros. Only opening the substrate as
  a *third-party* `@derive(MyFormat)` extension point depends on the staged
  `@derive` user-macro / public-protocol question (D-0036); that stays a later
  step either way and does **not** gate building the substrate for json + csv.

**Decision (fork R — locked by the user 2026-10-20): build the substrate
first.** Rather than extract-on-second-use, build the shared Zap-level,
derive-driven codec/reader substrate as **phase 1**, then land `json` and `csv`
as consumers on top of it.
The rationale for deferring extraction was avoiding a premature, single-consumer
framework — but we have **two** fully-specced consumers (json and csv) up front,
so the substrate can be designed to serve both from the start, and the parallel
execution pace makes a few hours of sequencing cost nothing.
The scanner itself is **still not shared** — each format keeps its own
tokenizer/reader-of-bytes; only the codec protocol + incremental byte-reader are
the substrate.

### 5. Public API surface — summary

```python
# DOM (Python-familiar)
json.loads(s: str | bytes) -> Value
json.dumps(v: Value, indent: i64 = 0) -> str

# Typed (via @derive(Json); no generics needed)
@derive(Json) struct/enum ...
T.from_json(s: str | bytes) -> T
self.to_json() -> str
self.to_json_pretty() -> str

# Pull / streaming
json.scan(src: str | bytes) -> Scanner      # Iterator[Token]

# Fast-follow sugar once user generics (D-0017) land:
json.decode[T](s: str | bytes) -> T          # → T.__from_json_value__
json.encode(x) -> str                         # → x.__to_json_value__
```

### 6. `csv` (recommend: own fast-follow ticket)

`csv` shares **no code** with `json` and `json` v1 is already large, so split it
(fork C).
Proposed surface, mirroring Python's `csv` and reusing the Iterator protocol:

```python
csv.reader(src: str | bytes, delimiter: str = ",", quotechar: str = "\"")
    -> Iterator[list[str]]
csv.dict_reader(src, ...) -> Iterator[dict[str, str]]   # header row → keys
csv.writer(... ) / w.writerow(list[str]) / w.writerows(...)
csv.dict_writer(fields: list[str], ...)
```

A typed `@derive(Csv)` mirroring `@derive(Json)` is a later nicety, not part of
the csv core ticket.

## Rationale

- **Three modes, one core** mirrors how serde/`encoding/json`/msgspec actually
  ship: the schemaless and the typed users are different people, and the scanner
  is shared work either way (DECISIONS D-0056 lists all three as motivating).
- **Derive-generated methods instead of `json.decode[T]`** is the key move: it
  delivers the high-value typed path *now*, decoupled from staged user generics
  (D-0017), while `__from_json_value__`/`__to_json_value__` leave a clean seam for
  the generic sugar later.
  `@derive(Json)` as a compiler built-in (like `Eq`/`Ord`, D-0036) also avoids
  blocking on user compile-time macros (the hardest staged piece).
- **`Int`/`Float` split** honors Zap's static-typing pitch and makes exact integer
  decode possible, unlike a JS-style f64-only `Value`.
- **Recursive-descent before SIMD** trades peak throughput for correctness and a
  small, reviewable v1; the stable token API preserves the SIMD upgrade path.
- **Strict typed + lenient-on-unknown-keys** matches msgspec and real-world API
  clients (servers add fields; clients must not break).
- **DOM-map typed decode v1** keeps the first landing correct and small; the
  token-direct path is a measurable optimization, not a correctness requirement.

Alternatives rejected for v1: SIMD-first scanner (complexity/risk); f64-only
numbers (precision loss, fights typing); waiting on generics to ship
`decode[T]` (needlessly blocks AWS I#89 / web I#107); bundling csv (bloats the
json PR for no shared code).

## Compatibility

Additive: a new bundled module (`import json` accepted, not required, matching
`crypto`/`signal`/`gc`), a new built-in derive `@derive(Json)`, and two new
compiler-known enums `json.Value` / `json.Token`.
No existing syntax changes.
`design/0006` line 398 ("`@derive(Json)` remains deferred") is superseded by this
proposal once accepted.
The later generic `json.decode[T]`/`encode` sugar is purely additive over the
derive dunders.

## Implementation

Grounded in the I#121 seam (`crates/{sema/src,ir/src/lower,codegen/src}/modules/
<name>.rs` + one registry line each; a `zaprt.c` banner section per format's
scanner runtime).
Ordered **substrate-first** (fork R decision):

**Phase 1 — shared serde substrate (its own ticket).**
1. **Codec protocol + derive core**: a format-neutral visitor/sink interface and
   the shared derive-codegen machinery (field walking, key↔field mapping,
   `@default`/optional handling, enum tagging, error-path tracking) that *any*
   built-in format derive emits against — reusing struct field walking from
   `@derive(Eq/Repr)` and `match`-based enum codegen (D-0046). This is the bulk of
   the work and is done once here, not per format.
2. **Incremental byte-reader**: a Zap-level `io.Reader`-style pull source over
   `str`/`bytes`/socket, shared with netpoller/`http` (I#104/I#107).
3. **Type-hosting seam (fork G)**: let a module contribute compiler-known enum
   registrations (for `Value`/`Token` and the shared sink types), rather than
   block on the deferred `PRELUDE_SRC` source-injection path (noted in I#121's PR).

**Phase 2 — `json` on the substrate.**
4. **Scanner core** in `zaprt.c` (tokenizer: structural chars, strings+escapes,
   numbers per fork N, UTF-8) + the `json` module functions on the seam.
5. **DOM**: `json.Value` enum, `loads`/`dumps` folding tokens ↔ `Value`.
6. **`@derive(Json)`**: register the built-in derive as a thin format impl over
   the phase-1 sink (`from_json`/`to_json`/`__*_json_value__`).
7. **Public `Scanner`**: wrap the core tokens as a comma-ok `Iterator` (D-0048).

**Phase 3 — `csv` on the substrate.** csv-specific reader/writer + its sink impl +
(optionally) `@derive(Csv)`, reusing phase-1 wholesale.

**Golden tests** (phases 2–3): DOM round-trip; typed decode/encode over struct /
value struct / nested / list / dict / tuple / enum; rename + default +
unknown-key + deny_unknown; strict-error paths; big-number limits; streaming
constant-memory scan; csv reader/writer + dict variants. Both GC collectors (CI
matrix).

Phase boundaries touched: runtime ABI (new `zaprt.c` sections), IR lower (derive
codegen), sema (module + derive + type registration).
Parallel-safe with other stdlib modules (I#121 made module adds conflict-free);
rebase cost is the three registry arrays + one `zaprt.c` banner, per the crypto
(I#105) note.
**Verification:** `cargo fmt` (required before push — sub-sessions have tripped
CI's Format check), host `cargo test`, `make docker-test` both collectors,
`clippy -D warnings`.

## Decisions (locked 2026-10-20)

Every fork is resolved; recorded as an ADR in DECISIONS.md (D-0059).

- **R — ordering:** build the shared serde substrate first (phase 1, I#131), then
  `json` (phase 2, I#100), then `csv` (phase 3, I#132). The scanner stays
  per-format; only the codec protocol + byte-reader are shared. Third-party
  `@derive(MyFormat)` extensibility waits on the staged `@derive` user-macro
  protocol (D-0036) and is out of scope for these phases.
- **P — parser strategy:** recursive-descent for v1 (SIMD stage-1 a later,
  measured fast-follow behind the same token API).
- **N — number model:** split `Int(i64)` / `Float(f64)` with documented limits
  (out-of-`i64` → `Float`, lossy beyond 2^53); `BigInt`/`RawNumber` deferred.
- **Typed surface:** compiler built-in `@derive(Json)` generating
  `from_json`/`to_json` + `__*_json_value__` dunders now — no user generics, no
  user macros. Generic `json.decode[T]`/`encode` sugar is a fast-follow once user
  generics (D-0017) land.
- **T — typed decode impl:** `Value`→struct DOM-map for v1; token-direct fast path
  deferred.
- **S — public streaming:** ship the minimal pull `json.scan` / `Scanner`
  (Iterator[Token]) in v1; the incremental socket `Decoder` (I#104/I#107) is a
  fast-follow.
- **E — validation:** strict typed validation, lenient only on unknown keys
  (`@json(deny_unknown=true)` opts into strict); errors surface as exceptions
  whose message carries byte offset + JSON path, upgrading to a typed
  `json.DecodeError` when typed exceptions land.
- **G — seam/type hosting:** register `json.Value` / `json.Token` (and the shared
  sink types) as **compiler-known enums** contributed by the module, extending the
  I#121 seam — rather than block on the deferred `PRELUDE_SRC` source-injection.
- **C — csv scope:** its own ticket (I#132), landing as phase 3 on the shared
  substrate right after json — not bundled, not indefinitely deferred.

**No grammar change:** the entire surface (`@derive(Json)`, `@json(name=...)`,
`Value`/`Token` enums, field defaults, enum methods) uses existing EBNF
productions (`decorators`, `enum_def`, `field`, D-0036/D-0046); `docs/GRAMMAR.ebnf`
needs no new production.

**Deferred (fast-follow, not v1):** generic `decode[T]`/`encode`; token-direct
