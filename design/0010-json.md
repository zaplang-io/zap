# Proposal: `json` (and `csv`) standard-library modules

- **Author(s):** Claude (design session for I#100)
- **Last updated:** 2026-10-20
- **Status:** Draft
- **Discussion:** I#100 (parent I#79; scope set by DECISIONS.md D-0056)

> Formatting convention (from Go): wrap text near the 80-column mark and start
> each sentence on a new line.

## Abstract

A native (no-CPython) `json` module for Zap, offered in three coexisting access
modes layered on one streaming scanner core: a dynamic `json.Value` DOM with
Python-familiar `loads`/`dumps`, a compile-time typed codec driven by a new
built-in `@derive(Json)`, and a public pull/token scanner that ties into the
Iterator protocol (D-0048) for large or over-the-wire payloads.
This doc recommends a concrete v1 scope and flags the forks that need a decision
before implementation.
`csv` is specified here but recommended to split into its own fast-follow
ticket.

## Background

The reuse check in I#100 concluded `msgspec`/`orjson` are CPython C-extensions
and therefore not reusable for a bundled-std module (D-0056); `json` must be a
**native** implementation.
`msgspec` remains a *design reference* for the typed/schema-driven surface, not a
dependency.

`json` is high-leverage: it gates the official AWS package (I#89) and the
FastAPI-style web framework (I#107), both of which want **typed** request/response
structs.

What the language already provides (all landed) and what the design must respect:

- **Data-carrying enums** (D-0046, PR #62): `enum` with type-first named payload
  fields, value-first tagged representation, `match` exhaustiveness.
  *Non-generic* enums ship today — so a fixed-variant `json.Value` enum is
  expressible now.
- **Iterator protocol** (D-0048, PR #68) + **generators** (I#67, PR #118):
  comma-ok `__next__(self) -> (T, bool)`; a pull scanner can be an `Iterator`.
- **Decorators / `@derive`** (D-0036): built-in derives (`Eq`/`Ord`/`Hash`/`Repr`)
  are *compiler-known* codegen over struct fields, wired into sema + lower.
  Field/struct annotations (`@json(name=...)`, `@default`) are supported.
  Crucially, a built-in `@derive(Json)` needs **no user-macro machinery** — it is
  another compiler-known derive. `design/0006` line 398 lists `@derive(Json)` as
  "deferred"; this proposal un-defers it as the core of the typed path.
- **Module seam** (I#121, PR #122): per-crate `modules/<name>.rs` with a
  `ModuleCheck { name, check }` dispatch on `module.method(args) -> Option<Ty>`.
  `str`/`bytes` share the `ZapStr` runtime layout and both lower to `Ty::Ptr`.
  Built-ins `list`/`dict`/`set` exist.
- **Exceptions** (I#12/PR #40): `raise` currently carries a **string** message;
  typed exception classes are not yet first-class.

What is **staged, not landed**, and therefore cannot be depended on for v1:

- **User generics** (D-0017): so a generic `json.decode[T](s)` function and the
  generic `Option[T]`/`Result[T, E]` enums (`design/0006` line 585) are **not
  expressible yet**.
  This is the single biggest constraint on the typed surface and shapes the whole
  recommendation.

## Proposal

### 1. Architecture: one scanner core, three modes

```
                 ┌─────────────────────────────┐
   bytes / str → │  scanner core (tokenizer)   │  internal, SIMD-ready layering
                 └──────────────┬──────────────┘
          ┌──────────────┬──────┴───────┬────────────────┐
          ▼              ▼              ▼                 ▼
   json.loads →    @derive(Json)   json.Scanner     (fast-follow)
   json.Value DOM  from_json/      pull/token API   socket Decoder
                   to_json methods  (Iterator)       over netpoller/http
```

A single hand-written scanner produces JSON tokens.
`loads` folds tokens into a `Value` tree; the typed codec maps a `Value` into a
struct (v1) with a token-direct fast path as a later optimization; the public
`Scanner` exposes the tokens directly as an `Iterator`.
One scanner, one set of lexing/number/escape rules, one error surface.

**Parser strategy (fork P):** v1 uses a **simple recursive-descent / hand-written
scanner**, not a SIMD-first design.
Rationale: correctness, debuggability, no new dependency, and the design session
host (and CI) is memory-constrained.
The token API is defined so a simdjson-style SIMD "stage 1" structural scan can
replace the byte loop later **without changing** the token surface or any caller.
*Recommendation: recursive-descent for v1; SIMD a measured fast-follow.*

### 2. Dynamic DOM — `json.Value`

A fixed-variant data-carrying enum (expressible today, D-0046):

```python
enum Value:
    Null
    Bool(bool b)
    Int(i64 i)
    Float(f64 f)
    Str(str s)
    Array(list[Value] items)
    Object(dict[str, Value] fields)
```

**Number model (fork N):** split `Int(i64)` / `Float(f64)` rather than JS-style
"all numbers are f64".
A number literal with no fraction and no exponent that fits `i64` decodes to
`Int`; otherwise `Float`.
This matches Zap's typed ethos and lets typed decode into an `i64` field be exact.
*Limits (documented):* integers outside `i64` range decode to `Float` (lossy
beyond 2^53); arbitrary-precision `BigInt` and a lossless `RawNumber(str)` variant
for byte-exact round-trip are **deferred**.
*Recommendation: `Int`/`Float` split with documented limits.*

Object representation is `dict[str, Value]`; **key order is not preserved** in v1
(JSON objects are unordered).
An ordered-object option (riding the `collections` ordered dict, D-0056) is a
minor fast-follow if round-trip order matters for I#107.

Public DOM API (Python-familiar):

```python
json.loads(s: str | bytes) -> Value          # parse; raises on malformed input
json.dumps(v: Value, indent: i64 = 0) -> str  # indent=0 compact, >0 pretty
```

`Value` carries small ergonomic helpers (methods on the enum, D-0046 allows
them), e.g. `v.get(key) -> Value` (object index, `Null` if absent),
`v.at(i) -> Value`, `v.as_int()/as_str()/...` accessors that raise on a variant
mismatch.
Schemaless consumers `match` on `Value` directly with exhaustiveness checking.

### 3. Typed codec — `@derive(Json)` (the high-value path)

Because generics are staged, the typed surface is delivered as a **built-in
derive that generates methods on the type**, needing neither generics nor user
macros:

```python
@derive(Json)
struct User:
    i64 id
    str name
    @json(name="email_address") str email
    bool active = true          # @default via = ; missing key → this value
```

`@derive(Json)` generates, per type `T`:

- `T.from_json(s: str | bytes) -> T` — a type-associated constructor.
- `self.to_json() -> str` and `self.to_json_pretty() -> str`.
- internal dunders `__from_json_value__(v: Value) -> T` and
  `__to_json_value__(self) -> Value` (the DOM bridge; also the extension point for
  the future generic `json.decode[T]`).

v1 implements decode as **`Value` → struct mapping** (parse to DOM, then populate
fields) and encode as **struct → `Value` → string**.
This is simple and correct; a **token-direct** decode that skips the intermediate
`Value` (msgspec-style, zero intermediate allocation) is a perf **fast-follow**
(fork T).
*Recommendation: DOM-map for v1.*

**Field ↔ key mapping:**

- Default key = the exact field name.
- `@json(name="...")` renames one field.
- Struct-level `@json(rename_all="camelCase"|"snake_case")` is a **fast-follow**
  (nice-to-have, not v1).

**Optional / missing / null:**

- A field with a `@default` (the `=` form, D-0038) is optional: a missing key uses
  the default.
- A missing key with **no** default is a **decode error** (strict).
- Explicit `null` for a non-nullable field is a decode error; a future `Option[T]`
  field (when generics land) will be the way to say "nullable/absent", decoding
  `null`/absent to `None`.
- **Unknown keys are ignored by default** (forward-compatible, web-friendly);
  struct-level `@json(deny_unknown=true)` opts into strict rejection.

**Type coverage:**

| Zap type | JSON |
|---|---|
| `struct` / `value struct` | object (value struct decoded by value) |
| `i64`/`f64`/`bool`/`str` | number / number / bool / string |
| `list[T]` / `set[T]` | array |
| `dict[str, V]` | object |
| tuple `(A, B)` | array, by position (fixed arity) |
| data-carrying `enum` | **internally tagged** object (below) |
| payload-free `enum` | string (the variant name) |

**Enums / sum-types:** default **internally-tagged** representation — a
discriminant key plus the variant's payload fields:

```json
{ "type": "Circle", "r": 3.0 }
```

The tag key defaults to `"type"`, overridable with
`@json(tag="kind")` on the enum; decode `match`es the tag then populates the
variant's fields (reusing D-0046 construction).
**Adjacent** and **untagged** representations are deferred.

**Validation / error semantics (fork E):** typed decode is **strict**
(msgspec-like) — type mismatch, missing required key, bad enum tag, and (unless
`@default`) `null` are all errors.
The one lenient default is *ignore unknown keys*.
Errors **surface as exceptions**: v1 `raise`s a JSON error whose **string message**
embeds the byte offset and the JSON path (e.g. `$.users[2].id: expected int, got
string`), since typed exception classes are not yet first-class (I#12).
When typed exceptions land, this becomes a `json.DecodeError` carrying structured
`offset`/`path` fields — API-compatible.
*Recommendation: strict typed validation; exceptions with path+offset in the
message for v1.*

### 4. Streaming / pull — `json.Scanner`

The scanner core is internal regardless; the **fork S** is whether to expose a
public pull API in v1.
It is cheap once the core exists, so the recommendation is to ship a **minimal**
one in v1:

```python
enum Token:
    BeginObject; EndObject
    BeginArray;  EndArray
    Key(str k)
    Null
    Bool(bool b)
    Int(i64 i)
    Float(f64 f)
    Str(str s)

json.scan(src: str | bytes) -> Scanner   # Scanner is an Iterator[Token]
```

`Scanner` implements the Iterator protocol (D-0048) with comma-ok
`__next__(self) -> (Token, bool)`, so `for tok in json.scan(body):` just works and
consumes constant memory over a huge array/object.

**Incremental over the wire (fast-follow, ties to I#104/I#107):** a
`json.Decoder` that pulls bytes from an io reader / socket as they arrive from the
netpoller, so an HTTP body is parsed as it streams.
The pull core above is exactly what it is built on; it is deferred only to keep v1
bounded and because it co-designs with `http` (I#104).

### 5. Public API surface — summary

```python
# DOM (Python-familiar)
json.loads(s: str | bytes) -> Value
json.dumps(v: Value, indent: i64 = 0) -> str

# Typed (via @derive(Json); no generics needed)
@derive(Json) struct/enum ...
T.from_json(s: str | bytes) -> T
self.to_json() -> str
self.to_json_pretty() -> str

# Pull / streaming
json.scan(src: str | bytes) -> Scanner      # Iterator[Token]

# Fast-follow sugar once user generics (D-0017) land:
json.decode[T](s: str | bytes) -> T          # → T.__from_json_value__
json.encode(x) -> str                         # → x.__to_json_value__
```

### 6. `csv` (recommend: own fast-follow ticket)

`csv` shares **no code** with `json` and `json` v1 is already large, so split it
(fork C).
Proposed surface, mirroring Python's `csv` and reusing the Iterator protocol:

```python
csv.reader(src: str | bytes, delimiter: str = ",", quotechar: str = "\"")
    -> Iterator[list[str]]
csv.dict_reader(src, ...) -> Iterator[dict[str, str]]   # header row → keys
csv.writer(... ) / w.writerow(list[str]) / w.writerows(...)
csv.dict_writer(fields: list[str], ...)
```

A typed `@derive(Csv)` mirroring `@derive(Json)` is a later nicety, not part of
the csv core ticket.

## Rationale

- **Three modes, one core** mirrors how serde/`encoding/json`/msgspec actually
  ship: the schemaless and the typed users are different people, and the scanner
  is shared work either way (DECISIONS D-0056 lists all three as motivating).
- **Derive-generated methods instead of `json.decode[T]`** is the key move: it
  delivers the high-value typed path *now*, decoupled from staged user generics
  (D-0017), while `__from_json_value__`/`__to_json_value__` leave a clean seam for
  the generic sugar later.
  `@derive(Json)` as a compiler built-in (like `Eq`/`Ord`, D-0036) also avoids
  blocking on user compile-time macros (the hardest staged piece).
- **`Int`/`Float` split** honors Zap's static-typing pitch and makes exact integer
  decode possible, unlike a JS-style f64-only `Value`.
- **Recursive-descent before SIMD** trades peak throughput for correctness and a
  small, reviewable v1; the stable token API preserves the SIMD upgrade path.
- **Strict typed + lenient-on-unknown-keys** matches msgspec and real-world API
  clients (servers add fields; clients must not break).
- **DOM-map typed decode v1** keeps the first landing correct and small; the
  token-direct path is a measurable optimization, not a correctness requirement.

Alternatives rejected for v1: SIMD-first scanner (complexity/risk); f64-only
numbers (precision loss, fights typing); waiting on generics to ship
`decode[T]` (needlessly blocks AWS I#89 / web I#107); bundling csv (bloats the
json PR for no shared code).

## Compatibility

Additive: a new bundled module (`import json` accepted, not required, matching
`crypto`/`signal`/`gc`), a new built-in derive `@derive(Json)`, and two new
compiler-known enums `json.Value` / `json.Token`.
No existing syntax changes.
`design/0006` line 398 ("`@derive(Json)` remains deferred") is superseded by this
proposal once accepted.
The later generic `json.decode[T]`/`encode` sugar is purely additive over the
derive dunders.

## Implementation

Grounded in the I#121 seam (`crates/{sema/src,ir/src/lower,codegen/src}/modules/
json.rs` + one registry line each; a `zaprt.c` banner section for the scanner
runtime):

1. **Scanner core** in `zaprt.c` (tokenizer: structural chars, strings+escapes,
   numbers per fork N, UTF-8), plus the module functions on the seam.
2. **`json.Value` / `json.Token` enums**: these are *named types*, which the seam
   does not currently register (it dispatches `module.method`).
   **Seam extension (fork G):** let a module contribute compiler-known enum
   registrations, rather than block on the deferred `PRELUDE_SRC` source-injection
   path (noted in I#121's PR).
   Recommend compiler-registered enums.
3. **DOM**: `loads`/`dumps` folding tokens ↔ `Value`.
4. **`@derive(Json)`**: new built-in derive in the derive machinery (sema typing +
   lower codegen of `from_json`/`to_json`/`__*_json_value__`), reusing struct
   field walking from `@derive(Eq/Repr)` and `match`-based enum codegen (D-0046).
   This is the bulk of the work.
5. **Public `Scanner`**: wrap the core tokens as a comma-ok `Iterator` (D-0048).
6. **Golden tests**: DOM round-trip; typed decode/encode over struct / value
   struct / nested / list / dict / tuple / enum; rename + default + unknown-key +
   deny_unknown; strict-error paths; big-number limits; streaming constant-memory
   scan. Run under both GC collectors (CI matrix).

Phase boundaries touched: runtime ABI (new `zaprt.c` section), IR lower (derive
codegen), sema (module + derive + type registration).
Parallel-safe with other stdlib modules (I#121 made module adds conflict-free);
rebase cost is the three registry arrays + one `zaprt.c` banner, per the crypto
(I#105) note.
**Verification:** `cargo fmt` (required before push — sub-sessions have tripped
CI's Format check), host `cargo test`, `make docker-test` both collectors,
`clippy -D warnings`.

## Open issues (the forks for the user to lock)

- **P — Parser strategy:** recursive-descent v1 *(rec)* vs SIMD-first.
- **N — Number model:** `Int(i64)`/`Float(f64)` split with documented limits
  *(rec)* vs f64-only vs lossless `RawNumber`.
- **Typed surface:** derive-generated `from_json`/`to_json` methods now *(rec)* vs
  wait for generics to ship `json.decode[T]`.
- **T — Typed decode impl:** DOM-map v1 *(rec)* vs token-direct fast path in v1.
- **S — Public streaming API:** ship minimal `json.scan`/`Scanner` in v1 *(rec,
  but genuinely optional)* vs defer all public streaming to fast-follow (core
  stays internal either way).
- **E — Validation:** strict typed + lenient-unknown-keys, errors as exceptions
  with path+offset message *(rec)*.
- **G — Seam/type hosting:** register `Value`/`Token` as compiler-known enums
  *(rec)* vs wait for deferred `PRELUDE_SRC` source injection.
- **C — csv scope:** split csv to its own fast-follow ticket *(rec)* vs bundle
  into the json v1 PR.
- Deferred (fast-follow, not v1): generic `decode[T]`/`encode`; token-direct typed
  path; SIMD stage-1; incremental socket `Decoder` (I#104/I#107); `rename_all`;
  adjacent/untagged enum reps; ordered objects; `BigInt`; typed `json.DecodeError`;
  `@derive(Csv)`.
