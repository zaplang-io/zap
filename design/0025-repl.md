# Proposal: `zap repl` — an interactive REPL and the shared session engine

- **Author(s):** REPL lane (I#159)
- **Last updated:** 2026-10-24
- **Status:** Under review
- **Discussion:** I#159 (tooling epic I#157); consumers I#234 (doctests), I#238 (playground)

> Formatting convention (from Go): wrap text near the 80-column mark and start
> each sentence on a new line.

## Abstract

`zap repl` adds an interactive read-eval-print loop to the toolchain.
Because Zap is statically typed and compiled AOT through LLVM, a REPL must
type-check and *execute* each entry while persisting typed state across
entries.
This note recommends executing each entry through an **in-process LLVM
ORCv2 JIT** that reuses the real `AST → ZIR → LLVM` backend, so REPL code has
**identical semantics to compiled code** (same monomorphization, value-struct
layout, exception model, and Immix GC).
It lays out the session-state, auto-print, error-recovery, and
GC/runtime-lifetime stories grounded in the current tree, rejects a second
(interpreter) semantics, and factors the core into a reusable `Session` engine
that I#234 (doctests) and I#238 (playground) consume.
It is **design-first**: the engine is architecturally load-bearing, so this
note stops for review before the JIT engine is built, and proposes a short
de-risking spike as the first implementation step.

## Background

### The pipeline today (verified against the tree)

The compile path is a straight line, all reusable:

```
source
  └─ zapc_syntax::parser::parse_str(src) -> (Module, ParseErrs, LexErrs)
  └─ zapc_sema::check(&module)           -> Vec<Diagnostic>   (ZAPnnnn, no LLVM)
  └─ zapc_ir::lower_module(&module)      -> (ZIR, LowerErrs)   (host-safe)
  └─ zapc_codegen (LLVM 18 via inkwell)  -> object file
  └─ cc link with the C runtime          -> native executable
  └─ run
```

- `crates/driver/src/lib.rs`: `front_end()` runs lex+parse+sema and prints
  `error[ZAPnnnn]:` diagnostics; `compile()` then lowers and calls
  `backend()` → `zapc_codegen::build_executable(module, out)` →
  `Command::new(exe).status()`.
- `crates/codegen/src/lib.rs`: `Backend::compile_object` lowers ZIR, builds an
  `inkwell` `Context`/`Module`, creates a native `TargetMachine`, verifies, and
  writes an **object file**; `build_executable` then writes the C runtime
  (`zaprt.c` + `zapgc.inc.c`) into a temp dir and links everything with `cc`.
- The entry point: a Zap `def main()` is emitted as the C `int main(void)`
  (`f.is_main` in codegen); GC initializes in a `__attribute__((constructor))`
  (`zap_gc_init` in `zaprt.c`); the M:N scheduler lazy-inits via
  `zap_sched_init`; an uncaught exception reaches `zap_uncaught`, which prints
  to stderr and **`exit(1)`s**.
- **Auto-print is already type-directed.** `Inst::Print` in codegen switches on
  the *static ZIR type* of each argument: `Ty::Ptr` → `zap_print_str`, floats →
  `%f`, ints → `%lld`. There is **no universal runtime `repr`** — the renderer
  is chosen at codegen time from the type the checker inferred. This is a
  decisive fact for auto-print (see §Proposal).

### What makes a Zap REPL hard

1. Every entry must be type-checked *in the context of all prior entries*
   (their inferred types, defs, imports), then compiled and run.
2. State must persist: `let` bindings, `def`s, `type`/`enum` decls, and imports
   from earlier entries must be visible and *live* (not collected) later.
3. The precise Immix GC roots through a codegen-emitted **shadow stack** +
   safepoints. Values held only in session bindings sit on *no* shadow-stack
   frame while the REPL waits at the prompt, so they need an explicit
   persistent-root mechanism.
4. A runtime exception must not kill the session — but `zap_uncaught` currently
   `exit`s the process.

## Proposal

### Execution model — recommendation: (a) in-process LLVM ORCv2 JIT

Run every entry through the existing `AST → ZIR → LLVM` backend, JIT-compiled
into one long-lived process. This is the Swift-REPL / cling model and the one
I#159 already sketches; this note confirms it against the tree and specifies
the state/error/GC mechanics.

**Why (a):**

- **One semantics.** The entry is translated by the same ZIR→LLVM code that
  AOT builds use, so monomorphization, value-struct layout, exceptions, and GC
  behave identically to `zap run`. This is the central requirement for a
  "prototype == ship" language and the reason the interpreter is rejected.
- **Run-once side effects.** Each entry executes exactly once; prints, I/O, RNG
  draws, and counters happen once (contrast (b) below).
- **Live persistent state.** Bindings are real LLVM globals in the JIT; they
  stay live across entries with no replay.
- **Type-directed auto-print falls out for free.** Because the REPL type-checks
  each entry, it has the static type of a trailing expression and can emit the
  *same* `Inst::Print`-style, type-directed rendering the compiler already uses
  — no new runtime `repr` is required for the first cut.
- **Fast after warmup.** Per-entry cost is LLVM compile of one small module
  (ms), not a `cc` link (contrast (b)).

The task note frames the "bulk of the effort" accurately: it is the
**incremental-compilation session** (cross-module symbol resolution,
redefinition/shadowing, persistent GC roots, generics-on-demand), not the ORC
wiring itself.

### Alternatives considered

**(b) Recompile-and-run the accumulated session each entry.**
Synthesize a module from all accumulated decls + a `main` wrapping the replayed
statements + the new entry, and drive the existing `build_executable` end-to-end
in a fresh process.

- Pros: simplest possible; reuses AOT verbatim; **zero new dependencies**; GC
  and scheduler "just work" because each run is a fresh process; perfect
  semantics by construction.
- Cons that are *fundamental*, not polish:
  - **Side effects re-run every entry** — prior prints repeat, files are
    re-written, RNG advances, counters double. Swallowing prior *stdout* does
    not stop external effects. This breaks the mental model for any stateful
    session.
  - **Latency grows O(n)** with session length (every entry recompiles and
    re-links the whole history) and each entry pays a full `cc` link (≈ seconds).
  - **State that is not a reconstructible pure value cannot replay** — open
    files, sockets, live coroutines, mutable aliased heap graphs.
- Verdict: **rejected as the model, retained as the fallback** if the ORCv2
  spike (below) shows the JIT path is not viable on LLVM 18 / inkwell 0.5. It is
  also a legitimate *Phase 0* to ship the `Session` engine API + test harness
  early for I#234 doctests (where snippets are self-contained and effects-once
  matters less), with the REPL proper landing on (a).

**(c) Tree-walking / bytecode interpreter over the AST/ZIR.**

- Pros: instant startup, no LLVM at eval time, trivially embeddable (nice for a
  WASM playground).
- Cons: **a second semantics implementation.** It would re-implement typing
  edge cases, value-struct layout, exception unwinding, generics
  monomorphization, and GC behavior, and would *drift* from codegen while
  exercising none of it. For a language whose pitch is "what you prototype is
  what ships," two executors is a correctness and trust hazard.
- Verdict: **rejected**, explicitly and on the record, per I#159.

### Session model (for the recommended JIT path)

A `Session` owns:

- **Accumulated declarations** as AST/ZIR: `def`s, `type`/`enum`/interface
  decls, and imports, kept so each new entry type-checks against them.
- **A binding table**: `name → { ty: Ty, generation: u32, storage: GlobalRef }`.
  The newest generation of a name wins (shadowing); older globals remain,
  harmless.
- **The live JIT** (one ORCv2 `JITDylib`), its process-wide runtime, and the
  persistent-root registry.

Per entry (generation `N`):

1. Splice the entry's source onto the session's accumulated top-level context
   and run the front-end (`parse_str` → `check`). Comments/trivia are irrelevant
   here.
2. If diagnostics contain errors, print them and **discard** the entry
   (no state mutation). This step is pure Rust; nothing can corrupt the session.
3. Otherwise classify the entry:
   - new `def`/`type`/import → add to accumulated decls;
   - `let`/assignment → allocate a module-level global `name$N`, record the
     binding, register it as a persistent GC root if its type holds pointers;
   - a trailing bare expression of non-unit type → store its value into
     `__val$N` and emit a type-directed print of it (auto-print).
4. Lower *only the new code* to a fresh LLVM module (prior defs already live in
   the JIT), wrap the entry's statements in a `__entry$N()` thunk, add the
   module to the JIT, look up `__entry$N`, and call it through the
   error-trapping boundary (below).

**Redefinition / shadowing.** `let x = 1` then `let x = "s"` creates `x$1`
(i64) and `x$2` (ptr); the binding table maps `x → x$2`. A redefined `def f`
likewise gets a new mangled symbol and the table repoints `f`; old callers
already compiled keep calling the old symbol (hot-reload of live dependents is
**deferred**, matching I#159's MVP line).

### Auto-print / value display

- A trailing expression is rendered with the **same type-directed logic as
  `Inst::Print`** (scalars via `%lld`/`%f`, `str`/pointer-to-str via
  `zap_print_str`). The checker's inferred type picks the renderer.
- First cut renders: integers, floats, bool, `str`, and the built-in
  collections that already have a `str()`/print rendering. Enums with a derived
  `repr` use it.
- User structs/interfaces with no Display fall back to a `<TypeName @ 0x…>`
  placeholder in the first cut; a general `repr` protocol is a **follow-up**
  (and is shared with `print()` work, not REPL-specific).
- A `:type <expr>` meta-command prints the inferred type without executing —
  a strong teaching feature for a typed language, and free (it is the sema
  result).

### Error handling (per entry, session survives)

- **Compile-time** (lex/parse/name/type/lowering): already surfaced as
  `Diagnostic` with stable `ZAPnnnn` codes (I#239). The REPL reuses the driver's
  formatting, prints `error[ZAPnnnn]: …`, and leaves session state untouched.
- **Runtime** (uncaught Zap exception): entries are invoked through a new
  runtime boundary `zap_repl_call(thunk) -> status` that wraps the thunk in the
  existing Itanium/SEH landing-pad machinery (`zap_eh_begin_catch` /
  `zap_eh_end_catch`) and, instead of `zap_uncaught`'s `exit(1)`, converts an
  escaped exception into a returned error + message. The REPL prints
  `Uncaught exception: …` and returns to the prompt. (`zap_uncaught` keeps its
  `exit` semantics for normal programs; the REPL installs the non-exiting
  variant.)
- **Hard faults** (segfault, `abort`, stack overflow in native code): **cannot**
  be caught and will end the session. Documented limitation, same as every
  native-code REPL (Swift/cling included).

### GC and coroutine runtime lifetime

- The runtime is initialized **once** for the REPL process. GC init runs when
  the runtime loads (its constructor); the scheduler lazy-inits on first use.
  All entries share one heap and one scheduler.
- **Persistent roots are the one genuinely new runtime piece.** Session-binding
  globals hold live values between entries while sitting on no shadow-stack
  frame, so under the precise Immix collector they must be registered in a
  **global-roots table** (`zap_gc_add_root(slot)` / scanned at every GC). Within
  an entry thunk, ordinary shadow-stack frames + safepoints already work because
  JIT code emits them identically to AOT. Under the Boehm fallback, globals are
  conservatively scanned, so the table is a no-op there.
- **Runtime symbol availability.** The JIT must resolve `zap_*` runtime symbols.
  Two options, decided in the spike: (i) link the runtime into the `zap` binary
  and expose process symbols to the JIT's symbol resolver; (ii) compile
  `zaprt.c` once to a dylib at REPL startup and load it into the `JITDylib`.
  (i) is simpler and keeps GC/scheduler state in-process; preferred unless
  symbol-visibility issues force (ii).
- **Async (stretch, deferred):** pump the scheduler between prompts so `go f()`
  spawned at the REPL can make progress; MVP runs coroutines only within the
  entry that spawns them, and cross-entry join is deferred.

### Multi-line / continuation input

Python-ish. The reader accumulates lines until the buffer forms a complete
top-level unit, using two signals:

1. **Lexical balance** — unbalanced `()[]{}`, an open triple-quoted string, or a
   trailing `\` continuation ⇒ keep reading.
2. **Block openers** — a logical line ending in `:` (`def`/`if`/`for`/`while`/
   `with`/`try`/`match`/type/enum headers) opens an indented block; by the
   interactive convention, a blank line (or a dedent to column 0) closes it.

When incomplete, the prompt switches from `zap> ` to `...  `. The parser's
own "unexpected EOF / expected indented block" error is used as a secondary
confirmation that the unit is truncated rather than wrong.

### First cut: supported vs deferred

**Supported (MVP):** scalars/operators, `let` + assignment, `print`, function
calls, `def`, `if/for/while/with/try`, closures capturing session bindings,
`type`/`enum`/interface decls, stdlib imports, `raise`/`try` with per-entry
recovery, auto-print of scalars/str/bool/collections, meta-commands
`:type :help :load :reset :quit`, multi-line input.

**Deferred:** hot-reload of a `def`/`type` with already-compiled live
dependents; cross-entry coroutine scheduling/join; a general `repr` protocol for
arbitrary user types; precompiled/cached prelude image for faster startup;
readline editing + persistent history (see dependencies).

### Reuse by I#234 (doctests) and I#238 (playground)

The core is a **`Session` engine** with a narrow, backend-agnostic API:

```rust
let mut s = Session::new()?;               // inits runtime + JIT once
let out: EvalOutcome = s.eval(src);        // one entry / snippet
// EvalOutcome { diagnostics: Vec<Diagnostic>,  // ZAPnnnn
//               stdout: String,
//               value: Option<String>,         // rendered auto-print
//               runtime_error: Option<String> }
```

- **I#234 doctests** drive `eval` snippet-by-snippet and assert on
  `stdout` + `diagnostics` (+ `value`); self-contained snippets don't need
  persistence, so doctests can even ride the (b) fallback early if needed.
- **I#238 playground** wraps `Session` behind a server/sandbox boundary and
  streams `stdout`; REPL-mode playground uses the same persistence as the CLI.
- The `zap repl` CLI is a thin reader-loop over this API. The engine, because it
  pulls LLVM, lives **behind the `codegen` feature** exactly like `zapc_codegen`
  — a host-only (no-LLVM) toolchain build has no REPL, identical to how it has
  no `zap run` today.

## Rationale

- **Single semantics** is the governing constraint (project memory; I#159). It
  eliminates (c) outright and is the strongest argument for (a) over any
  interpreter.
- (a) beats (b) not on polish but on two fundamentals: **effects run once** and
  **latency does not grow with the session**. (b) is kept only as a spike
  fallback / early engine-API vehicle.
- Auto-print is type-directed in the existing codegen, so reusing codegen makes
  display almost free, whereas an interpreter would have to re-derive it.
- Decisions to record if accepted: a new `D-00NN` for the REPL execution model
  (JIT, single semantics, persistent-roots runtime addition, engine behind the
  `codegen` feature).

## Compatibility

- Purely additive: a new `zap repl` verb and a new `Session` engine module.
- The compile path and all existing goldens are **unchanged**.
- One **runtime ABI addition** (RUNTIME-ABI.md): the global-roots table
  (`zap_gc_add_root`) and the non-exiting `zap_repl_call` boundary. Both are
  pay-only-when-used and do not alter existing program builds.
- Any new `.zap` fixtures must pass `zap fmt --check` (fmt-gate).

## Implementation

Phased, after design sign-off:

0. **De-risking spike (first step, ~1 day):** confirm the LLVM 18 / inkwell 0.5
   JIT surface — whether inkwell's *safe* API covers ORCv2/LLJIT or whether the
   JIT must use MCJIT (`create_jit_execution_engine`) or drop to raw `llvm-sys`
   bindings for an ORCv2 `JITDylib`. Prove: (i) JIT a trivial module that calls a
   `zap_*` runtime symbol and prints; (ii) a global defined in module A is read
   by module B in the same JIT; (iii) a GC root held only in a global survives a
   forced collection under precise Immix. **Report back before building the full
   engine** — the spike result may adjust the choice.
1. `Session` engine + `EvalOutcome` behind the `codegen` feature; runtime
   init-once; persistent-root registration; `zap_repl_call` + `zap_gc_add_root`
   in `zaprt.c`/`zapgc.inc.c`.
2. Entry classification, global allocation, shadowing, auto-print (reusing the
   `Inst::Print` type-directed renderer).
3. The `zap repl` CLI: reader loop, multi-line continuation, prompts,
   meta-commands.
4. Tests: scripted stdin sessions (define→use next line; shadow/redeclare;
   type error → session survives with the right `ZAPnnnn`; runtime exception →
   recovery; a multi-line block; a closure capturing a session binding) assert
   transcripts + exit behavior. Keep all existing goldens unchanged.

Phase boundaries touched: **RUNTIME-ABI** (two additive entry points). IR schema
unchanged. Gates for the implementation PR: `cargo fmt`; clippy both configs
(`--all-targets -D warnings`); full `make docker-test` under both collectors;
in-container clippy both configs; `zap fmt --check tests/golden`; confirm both
CI triggers (pull_request AND push) green before reporting.

### Dependencies

- **JIT:** no new crate — `inkwell` (LLVM 18) is already the backend binding.
  *Risk, flagged honestly:* inkwell's **safe** JIT surface is historically
  MCJIT-centric; its ORCv2 coverage may be thin, so the spike must decide
  between MCJIT, inkwell's ORC wrappers, and raw `llvm-sys`. This does not add a
  dependency (llvm-sys is already transitive), but it affects effort.
- **Line editor:** `rustyline` is the obvious choice for history/editing, but
  the house style is minimal-deps. **Recommendation:** ship the first cut with a
  **plain stdin line reader** (no new dep) — it also makes the scripted-stdin
  test harness trivial — and treat rustyline (editing + persistent history) as a
  deferred, optional enhancement gated to the REPL binary.

## Spike outcome (2026-10-24) — model refined, still (a)

The de-risking spike ran in the LLVM 18 dev container
(`crates/codegen/examples/jit_spike.rs`, throwaway). Results:

- **No safe ORCv2 in inkwell 0.5.** The crate exposes only MCJIT via
  `ExecutionEngine` (`create_jit_execution_engine`, `add_module`,
  `add_global_mapping`, `get_function`) plus a vestigial OrcV1 wrapper. ORCv2
  would mean dropping to raw `llvm-sys`. **Decision: use MCJIT.** It satisfies
  every REPL requirement; the "ORC" in the issue title was aspirational.
- **Proved in-container on LLVM 18 / inkwell 0.5:** (A) JIT-compile + call a
  function; (B) a second module added to the same engine reads a global defined
  in the first module (= the mechanism for persisting state across entries);
  (C) JIT'd code calls a process symbol (libc `puts`) — the mechanism for
  calling the `zap_*` C runtime, which is linked into `zap`. All three pass.
- **GC roots already exist.** `zap_gc_add_root(void **slot)`
  (`zapgc.inc.c`) registers a slot address that root enumeration feeds to
  `zap_process_slot` (mark **and** forward, so evacuation-safe); it is a no-op
  macro under Boehm. Session bindings need **no new GC work** — just register
  each binding slot once.

**One mechanism refinement this forces.** The ZIR `Module` has **no
module-level globals** (only structs/funcs/fn_sigs/interfaces), and top-level
`let`s fold into `main`. So bindings cannot be "LLVM globals threaded from ZIR"
as sketched above. Instead, a session binding becomes a **runtime session-slot**
(a `void*`/`i64` slot owned by the runtime, GC-rooted via the existing
`zap_gc_add_root`): the entry thunk reads referenced prior bindings from their
slots on entry and writes new/updated bindings back on exit. This is
backend-agnostic (helps the #238 playground / #234 doctests), reuses the
existing GC-root infra, and keeps the ZIR schema unchanged. It does require a
small new surface: sema resolves a session-binding name to a slot + type; ir/
codegen emit slot load/store intrinsics (`zap_repl_slot_get/set`); the runtime
owns the slot table. Scalars, `str`, collections, and closures (all `i64`/`ptr`)
are in the first cut; by-value structs in slots are deferred.

Net: the **execution model is unchanged** (in-process JIT reusing codegen,
single semantics); only the JIT API (MCJIT) and the binding storage (runtime
slots, not LLVM globals) are pinned down. The two runtime additions are now
`zap_repl_call` (non-exiting entry boundary) and `zap_repl_slot_get/set`
(+ `zap_gc_add_root`, already present).

## Open issues

- Runtime-symbol strategy: link-into-`zap` + process resolver vs a loaded
  runtime dylib (spike).
- General `repr`/Display protocol for user types — shared with `print()`, likely
